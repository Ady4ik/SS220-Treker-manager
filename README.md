# SS220 Treker Manager

Discord-бот для переноса всего Discord Forum в GitHub Issues и GitHub Projects v2 по команде `/migrate`.
Форум: `https://discord.com/channels/1097181193939730453/1385519706781253632`.

## Возможности

- `/migrate` по умолчанию использует `operation:sync_forum`: читает активные и архивные посты, но **обновляет только связанные Issue**, новые не создаёт.
- `/migrate operation:create_issue source:<ссылка на форум>` создаёт отдельный новый Issue для каждого поста. **Повторный create создаёт новые Issue**, это намеренная операция, а не синхронизация.
- Ссылка на пост читает весь пост и его ответы. Ссылка на конкретный комментарий по умолчанию читает **только этот комментарий**.
- `scope:post` читает весь пост даже по ссылке на комментарий; `scope:message` требует конкретную ссылку на сообщение. Ключи поста и отдельного комментария различаются.
- `баг/bug` → label `bug`; `фича/feature` → `enhancement`. Неизвестный или конфликтующий тип возвращает ошибку.
- Summary — краткая выдержка до 600 символов. Основной текст сохраняется и разбивается по известным полям: описание, шаги, ожидаемый/фактический результат, окружение. Это локальный разбор без LLM.
- Отдельный маршрут каждого типа задаёт репозиторий, дополнительные labels, Project и Status. Недостающие labels создаются.
- В Issue записывается видимый блок **«Источник Discord»**: ссылки и ID сервера, форума, поста и сообщения, область `post/message`. Для обычного текстового канала поля форума отсутствуют. Ссылки на вложения сохраняются без скачивания файлов и могут истечь.
- Длительный обход работает фоном и имеет `/migration-status`; отчёт хранится в `data/jobs`.
- SQLite и маркеры источника позволяют продолжить после сбоя через **sync_forum**, не создавая новый Issue.
- `DRY_RUN=true` показывает результат разбора без запросов к GitHub.

## Создать новое или дополнить существующее

```text
# Создать новый Issue из поста:
/migrate operation:create_issue source:<ссылка на пост>
# Создать новый Issue только из выбранного комментария:
/migrate operation:create_issue source:<ссылка на комментарий> scope:message
# Обновить связанные Issue постов всего форума, пропустить ещё не перенесённые:
/migrate operation:sync_forum source:<ссылка на форум>
# Дополнить Issue #42 конкретным комментарием из того же форума:
/migrate operation:sync_forum source:<ссылка на комментарий> scope:message issue_number:42
```

Короткие команды: `/forum-sync source:<ссылка>` и `/issue-from-source source:<ссылка>`.
`issue_number` разрешён только для синхронизации конкретного поста/сообщения и относится к репозиторию из маршрута. Бот проверяет совпадение сервера и форума с метаданными Issue. Источник, уже связанный с другим Issue, автоматически не перепривязывается. Совпадение только форума **не означает**, что все посты должны попадать в один Issue: для добавления нового источника нужен явный `issue_number`.

Связи хранятся в SQLite: `migrations` — текущий Issue источника, `source_bindings` — репозиторий, номер Issue и JSON происхождения. В Issue остаются скрытые versioned JSON-метаданные и стабильный маркер. При потере базы бот ищет точный маркер в GitHub; если найдено несколько Issue, требует `issue_number`, а не выбирает случайный. Метаданные и служебные границы вручную удалять нельзя.

После повторного **create_issue** привязка для последующей синхронизации указывает на последний созданный Issue; предыдущие Issue сохраняются без изменений. Если создание прошло, но добавление в Project завершилось ошибкой, используйте **sync_forum**, а не повторный create. Если ответ создания потерялся по сети, sync ищет маркер в GitHub.

Синхронизация всего форума обновляет источники типа **post**. Отдельные Issue из комментариев обновляйте по ссылке на комментарий (они не смешиваются с Issue целого поста). `DRY_RUN` проверяет чтение и размер нового блока, но без обращения к GitHub не определяет, существует ли целевой Issue и подходит ли он для обновления.

## Настройка

Требуется Python 3.11+. В PowerShell:

```powershell
py -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
New-Item .env
New-Item routes.json
```

1. В Discord Developer Portal создайте application и bot. Включите **Message Content Intent**. Пригласите бота со scopes `bot` и `applications.commands`, правами View Channels, Read Message History, Send Messages и Send Messages in Threads. Для приватных тредов бот должен быть участником.
2. Укажите `DISCORD_TOKEN` в `.env`. `DISCORD_GUILD_ID` ускоряет регистрацию команды на тестовом сервере; без него команда глобальная и может появиться с задержкой.
3. Укажите `GITHUB_TOKEN`: например, classic PAT с `repo` и `project`, доступом к целевому репозиторию и Project. При использовании fine-grained PAT нужны Issues read/write и соответствующее разрешение Projects read/write у владельца; проверьте доступ к обоим ресурсам и SSO организации.
4. В `routes.json` замените примеры на реальные репозитории и борды. `project_number` — номер из URL `/users/OWNER/projects/N` или `/orgs/OWNER/projects/N`; `project_owner_type` — `user` или `organization`. `status_field` и `status` должны точно совпадать с названиями в Project. Удалите `status`, если нужно лишь добавление на борду.
5. Добавьте в `.env` `DISCORD_FORUM_CHANNEL_ID=1385519706781253632`, `DRY_RUN=true`, `ROUTES_FILE=routes.json` и `DATABASE_PATH=data/migrations.sqlite3`. Структуру `routes.json` возьмите из примера ниже. Запустите `.venv\Scripts\python -m bot` и проверьте `/migrate` в режиме dry-run. Затем установите `DRY_RUN=false` и перезапустите.

Минимальная структура `routes.json`:

```json
{
  "bug": {"repository": "OWNER/REPOSITORY", "labels": ["triage"], "project_owner": "OWNER", "project_owner_type": "organization", "project_number": 1, "status": "Todo"},
  "feature": {"repository": "OWNER/REPOSITORY", "labels": ["triage"], "project_owner": "OWNER", "project_owner_type": "organization", "project_number": 2, "status": "Todo"}
}
```

Репозиторий кода бота и репозиторий назначения Issue могут быть разными. Дополнительный аргумент `repository` должен совпадать с маршрутом данного типа. Другие теги не переносятся произвольно: нужные labels укажите в маршруте.

## Пример трекера

```text
Тип: баг
Заголовок: Не открывается шлюз
Описание: После подачи питания шлюз не реагирует на нажатие.
Шаги: Подать питание, нажать на шлюз.
Ожидаемый результат: Шлюз открывается.
Фактический результат: Нет реакции.
Окружение: Карта и номер раунда.
```

## Доступ и повторные команды

Команда доступна участникам с Manage Messages; право проверяется для каждого поста. Форум должен находиться на том же сервере и быть доступен вызывающему участнику и боту. Читаются активные и архивные посты через Discord API, а история каждого поста запрашивается с `limit=None`, поэтому ограничение в 100 сообщений не применяется.

Запускайте **один экземпляр** бота и сохраняйте каталог `data/`. Один форумный обход выполняется как фоновое задание; параллельный обход того же сервера блокируется. При синхронизации заменяется **только блок данного источника** между служебными границами `ss220-begin`/`ss220-end`. Ручные заметки вне блока, другие источники, заголовок, labels и состояние Issue сохраняются. Ручные изменения внутри блока будут перезаписаны. Перед обновлением бот читает актуальное тело с GitHub, а не из SQLite; одновременно редактировать Issue во время синхронизации не следует. Добавление в Project повторяется, Status устанавливается заново.

Старые Issue находят по прежнему маркеру: ключ поста совместим с ключом его первого сообщения в предыдущей версии. При первом обновлении старое тело без служебных границ сохраняется, новый управляемый блок добавляется ниже. Это может оставить старую копию истории; после появления нового блока её можно убрать вручную. Чужие Issue без метаданных не привязываются по одному лишь номеру.

### Запуск для этого форума

```text
/migrate operation:create_issue source:https://discord.com/channels/1097181193939730453/1385519706781253632
/migrate operation:sync_forum source:https://discord.com/channels/1097181193939730453/1385519706781253632
/migration-status job_id:<ID из ответа>
/migration-status job_id:<ID из ответа> report_file:true
```

Без `source` используется `DISCORD_FORUM_CHANNEL_ID`; если он не задан, команда внутри поста форума выбирает **весь родительский форум**. Для одного поста передайте его ссылку явно.

Задание читает сообщения, созданные до его запуска. Это не непрерывный мониторинг и не транзакционный снимок: удалённые сообщения недоступны, редактирование/перемещение постов во время обхода может менять результат. При чтении целого поста ответы не переопределяют тип и заголовок трекера. При выборе одного комментария тип берётся из тегов поста и самого комментария; при конфликте возвращается ошибка. Summary поста содержит выдержку исходного сообщения и первых ответов, полная история — всех доступных сообщений, включая текст embeds и ссылки на вложения.

Прогресс и ошибки каждого поста сохраняются в `data/jobs/<ID>.json` (путь меняется через `JOBS_DIRECTORY`). Отчёт содержит краткие выдержки сообщений, поэтому защитите доступ к этому каталогу. В Discord отчёт доступен только инициатору на исходном сервере; он не публикуется в общий канал. После перезапуска незавершённое задание помечается `interrupted`: повторите `/migrate` вручную. Ошибка одного поста не прерывает остальные; ошибка получения списка архива помечает весь обход как неполный (`failed`).

**Ограничение размера:** если полная история превышает бюджет в 60 000 символов тела Issue, пост читается, но не переносится и получает ошибку в отчёте. История не обрезается незаметно; автоматическое разбиение по комментариям пока не реализовано. Пустые/недоступные истории и неизвестные теги также отображаются в отчёте.

Если ответ создания Issue потерян по сети, следующая команда ищет маркер через список Issues. При удалении маркера и базы восстановление связи невозможно. Поиск в большом репозитории может быть медленным. Бот переносит сообщения с учётом доступа инициатора: видимость созданного Issue определяется целевым репозиторием.

`.env`, `routes.json` и `data/` исключены из Git. Токены в чат отправлять не нужно.

## Проверки

```powershell
.venv\Scripts\python -m pip install -r requirements-dev.txt
.venv\Scripts\python -m pytest -q
.venv\Scripts\ruff check .
```

Тесты используют подменённые API, не создают реальные Issues и не подключаются к Discord. Полный запуск требует ваших Discord/GitHub токенов и реальных маршрутов.
